# Organizer finance API (simulation)

All money is integer 1/100 KZT. These APIs move no real funds. Authentication and the existing organization `finance` permission (owner implicitly) are required for the event's organization. Reports/refund/scanner permissions alone do not grant finance access. No payout profile secrets are returned.

`GET /api/v1/events/{event_id}/finance` returns existing web fields event_id, currency, simulated, gross_minor, fees_minor, refunds_minor, estimated_payout_minor, generated_at, plus discount_minor, collected_minor, fulfilled_collected_minor, charged_fees_minor, fee_reversals_minor, pending_refunds_minor, activation_charges_minor, activation_refunds_minor, net_minor, balance_minor, reserved_minor, sent_minor, environments, simulation_only and payout_eligible_at. Gross/discounts and ticket cash/fee/refund amounts use the authoritative analytics purchase snapshots. Activation charges include all successful activation attempts, less separately reported completed activation refunds. Net is ticket net less net activation charges. Balance is net less historical sent payouts. Estimated payable is max(0, balance less pending ticket/activation refunds and reservations). Negative balance is retained after later refunds. Mixed/sandbox records are readable but cannot fund demo payouts.

`POST /api/v1/events/{event_id}/finance/payouts` requires Idempotency-Key and `{amount_minor: positive integer}`. Creates a pending simulation reservation if sufficient payable balance exists. `GET` on the same path lists history with limit (1..100), offset (>=0). `POST /.../payouts/{payout_id}/simulate` takes `{status: eligible|sent|failed}`. Pending -> eligible -> sent; pending/eligible -> failed. Pending reservations may be created before the event ends; eligibility and sending require server time >= event.ends_at (payout_eligible_at). This is an implementation default consistent with accepted activation terms that hold revenue until the event takes place, not a newly confirmed product rule. Repeating the current state is harmless; terminal results cannot be rewritten. Sending rechecks settled solvency under the event mutex. Refund initiation invalidates underfunded pending/eligible reservations. Event cancellation records all order refund liabilities before reconciling reservations once in the same event-locked transaction; absent reservations skip the event-wide cash aggregate. Successful refunds after a sent payout append one signed adjustment per refund and derive an adjusted display status, retaining the immutable sent payout row (transfer_status=sent). Adjusted counts as sent for balance. No real transfer or provider call exists. Simulation actions are available only in development/test.

Mutations lock idempotency, session, organization, event, then payout; audit and deduplicated localized payout-status notification intent commit atomically. Notifications go to the requester and recheck finance authority during fan-out. Errors: missing key 422, malformed input 422, unknown event/payout 404, missing finance permission 403, insufficient balance/mixed environment/invalid transition 409, changed payload with reused key 409. Read queries use a five-second statement timeout and repeatable-read snapshot without row locks.

Adjustment finance_entry rows link canonical refunds and saved fee reversals to the latest prior sent payout for reference history. Ticket/activation amounts remain derived from canonical records; these adjustment rows are not subtracted a second time. The payout debit entry is unique and is subtracted once. Sent payout rows and all finance entries are protected against updates/deletes by database triggers.


Finance entries are deliberately a minimal payout/adjustment history rather than a duplicated ledger of all commerce activity: existing canonical attempts, immutable item snapshots and refunds remain authoritative. A successful ticket refund appends a refund debit and saved fee-reversal credit; an activation compensation appends a positive activation_refund credit. Effects are linked to the latest prior sent payout, and adjusted is derived whenever adjustment history exists, even if its net amount is zero. Audit records identify the controlling user for API actions and the finance service for refund-driven adjustments. The two refund hooks cover voluntary/event cancellation refunds, late/duplicate/blocked ticket charges, and compensated activation charges under the existing event mutex. Unknown/failed refunds remain unresolved exposure.

Example: three KZT 4,000 tickets collect 1,200,000 minor units, retain 36,000 processing fee, and deduct 500,000 activation charge: net and maximum reservation 664,000. Sending leaves balance zero. A later full ticket refund reverses the 36,000 fee and leaves balance -1,164,000 while the historical 664,000 payout remains sent. No simulated transfer is repeated. Pending refunds conservatively reserve their full amounts until authoritative success.
